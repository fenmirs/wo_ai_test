# WoAiTest 优化计划

## 概述

基于现有代码库分析和讨论，确定以下四个优化方向。优先级从上到下排列。

---

## 一、应用级参数模板

### 目标
解决大量 API 重复填写相同参数（如 JWT 认证的 Authorization Header、Content-Type 等）的痛点。

### 设计要点

1. **模板存储位置**
   - 项目级存储，放在 `config.json` 中，不挂载到单个 API 上
   - 数据格式：
     ```json
     {
       "templates": [
         {
           "id": "tpl_jwt",
           "name": "JWT 认证",
           "sections": {
             "header": [
               { "key": "Authorization", "default": "Bearer {token}", "enabled": true },
               { "key": "Content-Type", "default": "application/json", "enabled": true }
             ],
             "param": [],
             "body": null
           }
         }
       ]
     }
     ```

2. **应用模板的交互方式**
   - 新增 API 时：如果存在模板，弹窗提示"是否应用模板？"，展示模板列表
   - 已有 API：在操作菜单/工具栏加"应用模板"按钮
   - **可部分应用**：弹窗中以 checkbox 列表展示模板下所有条目（Header/Param），用户勾选需要的项
   - 模式选择：**追加**（保留现有参数添加新条目）或 **覆盖**（移除对应 section 的全部现有项）

3. **入口位置**
   - 顶部菜单栏或底部栏加「模板管理」入口，类似环境变量管理
   - 管理页面支持：新建 / 编辑 / 删除 / 预览模板

4. **与场景的关系**
   - 模板应用于场景层面的 header/param/body，不涉及 API 级别的 method/path
   - 应用模板时：应用到当前场景，不修改其他场景

### 涉及修改的文件
- `ProjectManager.js` — 模板 CRUD
- `APIDetail.js` — 应用模板 UI + 逻辑
- `APIMain.js` — 新建 API 时触发模板选择
- 新增 `TemplateManager.js` 或 `components/TemplateDialog.js`

### 工作量估算
- 后端（ProjectManager）: ~150 行
- 前端 UI（模板管理 + 应用弹窗）: ~400 行
- 集成: ~100 行

## 二、cURL 导入功能

### 目标
允许用户直接粘贴浏览器/同事发来的 cURL 命令，自动解析为 URL + Method + Header + Body。

### 设计要点

1. **解析范围**
   - 支持 `curl -X POST https://api.example.com/v1/login`
   - 解析 `-H "Key: Value"` → Headers
   - 解析 `-d '{"key":"value"}'` 或 `--data-raw` → Body（raw JSON）
   - 解析 `-d "key=value&key2=value2"` → x-www-form-urlencoded
   - 解析 URL 后 `?key=value` 部分 → Params
   - 支持单引号/双引号包裹的值
   - 支持 `--data-binary`、`--form` 等变体

2. **入口位置**
   - 在左侧 API 树顶部加「导入 cURL」按钮
   - 或在新建 API 时提供"从 cURL 创建"选项

3. **交互流程**
   - 弹窗粘贴 cURL 文本
   - 自动解析并预览结果（方法、URL、Header 条目数、Body 预览）
   - 确认后创建一个新的完整 API（含一个默认场景）

4. **技术实现**
   - 纯前端解析，使用正则 + 状态机，不需要第三方库
   - 参考现有的 `ImportDialog.js` 的解析风格

### 涉及修改的文件
- 新增 `utils/CurlParser.js` — cURL 解析器（纯函数）
- 新增 `components/CurlImportDialog.js` — 导入弹窗
- `APIMain.js` — 加入口按钮
- `App.js` — 桥接导入流程

### 工作量估算
- cURL 解析器: ~200 行
- UI 弹窗: ~200 行
- 集成: ~100 行

## 三、Pre-request / After-response 脚本

### 目标
允许用户在请求发送前和响应接收后执行 JavaScript 脚本，处理签名生成、数据变换、动态断言等复杂逻辑。

### 设计要点

1. **交互位置**
   - 在现有 tab 栏新增「脚本」tab（位于断言之后、历史之前）
   - 分两个编辑区域：
     - **Pre-request Script**（请求前执行）
     - **After-response Script**（响应后执行）
   - 底部日志输出区域

2. **暴露的 API 对象（类似 Postman PM 风格）**
   ```js
   // Pre-request 可用
   pm.env.get('key')       // 读取环境变量
   pm.env.set('key', val)  // 设置环境变量
   pm.env.unset('key')     // 删除环境变量
   pm.request.headers      // 当前请求的 headers（可读写）
   pm.request.params       // 当前请求的 params（可读写）
   pm.request.body         // 当前请求的 body（可读写）

   // After-response 额外可用
   pm.response.status      // HTTP 状态码
   pm.response.headers     // 响应头
   pm.response.json()      // 解析 JSON 响应体
   pm.response.text        // 原始响应文本
   pm.test(name, fn)       // 断言测试
   ```

3. **沙箱方案选择**

   | 方案 | 优点 | 缺点 |
   |------|------|------|
   | Web Worker | 天然隔离，不会卡 UI，支持异步 | 不能直接访问 DOM，需消息通信 |
   | `Function()` + `with` | 实现简单 | 不安全，`while(1)` 会卡死 |
   | Electron `vm` 模块 | 比 eval 安全 | 仅在 Electron 环境可用 |
   | **Proxy + 沙箱对象** | 可控性好 | 需自行实现超时保护 |

   **推荐方案**：Proxy 封装沙箱对象 + `setTimeout` 超时保护（类似 Postman 早期的实现）。如果发现性能瓶颈再考虑 Web Worker。

4. **执行流程变更**
   现有：`点击发送 → ChainManager.resolve() → APIExecutor.execute()`
   变更为：`点击发送 → ChainManager.resolve() → **Pre-request Script** → APIExecutor.execute() → **After-response Script**`
   - Pre-request 修改的 `pm.request.*` 会传递到实际请求
   - After-response 可以修改环境变量供后续链调用使用
   - 与 ref 链的关系：Pre-request 执行在 ref 链解析之后，所以脚本里可以读取 ref 解析后的值

5. **超时保护**
   - 脚本执行超时上限 5 秒
   - 使用 `Promise.race` + `setTimeout` 实现

### 涉及修改的文件
- 新增 `utils/ScriptSandbox.js` — 沙箱实现
- `APIDetail.js` — 新增"脚本"tab + 编辑器 + 执行流程集成
- `APIExecutor.js` — 集成 pre/after 钩子
- `ChainManager.js` — 流程中插入脚本执行

### 工作量估算
- 沙箱实现: ~250 行
- UI 编辑器: ~300 行
- 执行流程集成: ~200 行

## 四、OpenAPI/Swagger 导入

### 目标
允许用户直接导入 Swagger 2.0 / OpenAPI 3.0 规范文件，自动生成完整项目结构（分组 + API + 参数 + Schema）。

### 设计要点

1. **支持的格式**
   - Swagger 2.0 (JSON/YAML)
   - OpenAPI 3.0 (JSON/YAML)
   - 输入方式：粘贴文本 / 上传文件 / 输入 URL

2. **映射规则**
   - Tag → 分组（支持层级 tag 命名如 `user/auth`）
   - Path + Method → API
   - Parameters → 根据 `in` 映射到 Param / Header / Body
   - RequestBody → Body (raw JSON)，附带 Schema
   - Responses → 存入 API 的 response schema 供断言参考

3. **导入流程**
   - 选择文件/粘贴 → 预览解析结果（展示 API 数量和分组结构）
   - 可选择需要导入的 API 列表（可部分导入）
   - 确认后批量创建 API

4. **与模板联动**
   - 导入时可选择"同时应用指定模板"，自动给所有导入的 API 添加通用参数

### 涉及修改的文件
- 新增 `utils/OpenApiImporter.js` — 解析器
- 新增 `components/OpenApiImportDialog.js` — 导入弹窗
- `APIMain.js` — 入口
- `ProjectManager.js` — 批量导入 API 方法

### 工作量估算
- OpenAPI 解析器: ~400 行
- UI + 预览: ~300 行
- 集成: ~150 行

## 路线图

```
阶段一（本次实现）
  └── 应用级参数模板 + cURL 导入
  └── 预计代码量: ~1050 行

阶段二（后续）
  └── Pre-request / After-response 脚本
  └── OpenAPI/Swagger 导入
```

## 关联性说明

模板和 cURL 导入有共通的前端模式（弹窗 + 条目可勾选预览），可以复用现有的 `ImportDialog` 组件风格和 `KVTable` 组件。脚本功能独立但基础设施（Monaco editor）已就绪。OpenAPI 导入解析复杂度最高但价值也大，可作为收尾。
