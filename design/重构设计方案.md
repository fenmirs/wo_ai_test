# WoAiTest 重构设计方案

> 基于多场景（Scenario）模型的 API 数据架构重构

---

## 一、背景与目标

### 1.1 现有问题

| 问题 | 描述 |
|------|------|
| 单 API 单配置 | 一个 API 只能存一套参数，无法同时保存多组测试用例 |
| Body 类型切换丢数据 | JSON ↔ XML 切换时 content/schema 互相覆盖 |
| 项目文件过大 | 所有 API 数据集中在一个 `config.json`，修改单个 API 要全量写回 |
| 删除无撤回 | 删除即消失，引用的级联处理不完善 |
| 无版本兼容 | 数据结构升级无标记，旧文件无法识别 |
| 搜索受限 | 搜索只能按名称/id 模糊匹配，无法按请求路径、场景路径搜索 |
| 无项目间切换 | 切换项目需重新加载，不缓存，响应慢 |
| 引用查找困难 | 无"查看引用"功能，删除前无法得知哪些 API 引用了目标 API |

### 1.2 改造目标

- 多场景支持：一个 API 下可定义 N 个独立场景，各自保存 method/params/headers/body/assertions
- Per-type 内容隔离：每个场景下的 body 按 contentType（json/xml/text/html）独立保存 content + schema
- 文件拆分：每个 API 独立文件，修改只写自身
- 逻辑删除 + 物理删除：删除先标记，永久删除才处理引用校验
- 版本兼容：config.json 带版本号，支持升级迁移
- 引用支持选择场景：`{{ref:apiId@scenarioId.fieldPath}}`
- 批量运行 + 文档生成：所有场景一键执行，文档包含各场景请求/响应对比
- 工作空间（Workspace）：欢迎页选择的是"配置目录"，内部可包含多个项目，切换项目零 I/O
- 全量预加载：项目加载时一次性读取所有 API config 到内存，搜索/引用完全走缓存
- 完整性检查（C 级）：加载时自动校验索引 ↔ 文件一致性，自动修复 + 友好提示
- 缓存优先 + 脏标记 + 自动保存：所有写操作只更新内存，由定时器统一落盘
- 路径模糊搜索：支持按 API 顶层 `api_path` 和场景级 `apiPath` 模糊搜索
- 引用查看：API 右键菜单新增"查看引用"，弹窗展示被引用的目标 API（按场景分组），可点击跳转

## 二、数据模型

### 2.1 项目配置文件 `config.json`

```json
{
  "version": 2,
  "projectName": "我的项目",
  "profile": [
    { "activate": true, "name": "dev", "domain": "192.168.1.1" }
  ],
  "groups": [
    { "id": "grp_001", "name": "认证模块", "parentId": null }
  ],
  "apis": [
    {
      "id": "api_001",
      "name": "获取 token",
      "group": "grp_001",
      "apiPath": "apis/api_001_config.json",
      "deleted": false
    }
  ]
}
```

关键点：
- `version` 字段供兼容迁移使用
- `apis` 只存索引，完整数据在 `apis/{apiId}_config.json`
- `deleted` 逻辑删除标记

### 2.2 API 数据文件 `apis/{apiId}_config.json`

```json
{
  "id": "api_001",
  "name": "获取 token",
  "group": "grp_001",
  "deleted": false,
  "scenarios": {
    "scn_default": {
      "id": "scn_default",
      "name": "默认场景",
      "description": "首次自动创建",
      "createdAt": "...",
      "updatedAt": "...",
      "deleted": false,
      "method": "POST",
      "apiPath": "{domain}{api-prj}/token",
      "header": [
        { "key": "Content-Type", "default": "application/json", "enabled": true }
      ],
      "param": [],
      "body": {
        "type": "raw",
        "activeContentType": "json",
        "contents": {
          "text": { "content": "", "schema": null },
          "json": { "content": "{\"username\": \"admin\"}", "schema": { ... } },
          "xml": { "content": "<root></root>", "schema": null },
          "html": { "content": "", "schema": null }
        }
      },
      "assertions": [
        { "expression": "$.code == 200", "enabled": true }
      ],
      "refChain": [
        { "refPath": "api_002@scn_default.data.token", "fieldLocation": "body.contents.json.content" }
      ]
    },
    "scn_001": {
      "id": "scn_001",
      "name": "异常参数-空密码",
      "description": "测试密码为空时的响应",
      "createdAt": "...",
      "updatedAt": "...",
      "deleted": false,
      "method": "POST",
      "apiPath": "{domain}{api-prj}/token",
      "header": [ ... ],
      "param": [],
      "body": {
        "type": "raw",
        "activeContentType": "json",
        "contents": {
          "json": { "content": "{\"username\": \"admin\", \"password\": \"\"}", "schema": { ... } }
        }
      },
      "assertions": [
        { "expression": "$.code == 400", "enabled": true }
      ]
    }
  },
}
```

关键点：
- `scenarios` 对象，key 为场景 ID
- `body.contents` 按 contentType 隔离存储
- `activeContentType` 标记当前激活的 body 格式
- `refChain` 在每个场景内部缓存引用关系，不同场景可独立依赖不同 API
- 引用变量写在哪个场景/字段中，`refChain` 就记录在哪个场景下

### 2.3 历史记录 `apis/{apiId}_history.json`

```json
[
  {
    "id": 1,
    "scenarioId": "scn_default",
    "scenarioName": "默认场景",
    "timestamp": "2026-05-13T10:30:00",
    "apiConfig": { ... },
    "result": {
      "success": true,
      "statusCode": 200,
      "elapsedTime": 235,
      "responseData": "...",
      "responseHeaders": {},
      "assertionResult": { "allPassed": true }
    }
  }
]
```

关键点：
- 每个 API 独立历史文件，不再有项目级 `history.json`
- 历史按 `scenarioId` 分组，当前场景只显示自己的历史

### 2.4 引用变量格式

```
{{ref:apiId@scenarioId.fieldPath}}
```

示例：
```
{{ref:api_login@scn_default.data.token}}
{{ref:api_order@scn_001.data.list[0].id}}
```

- `apiId` — 被引用的 API
- `scenarioId` — 被引用的场景（避免歧义，依赖执行时跑该场景）
- `fieldPath` — JSONPath 到具体字段

## 四、工作空间与缓存策略

### 4.1 概念定义

| 术语 | 说明 |
|------|------|
| 配置目录（Workspace） | 欢迎页选择的顶层目录，包含一个或多个项目。整个目录全量加载到内存 |
| 项目（Project） | 底部栏切换的基本单元，每个项目有独立的 `config.json` + `apis/` |
| 切换项目 | 纯内存操作，无 I/O，切换时校验当前项目是否有未保存草稿 |

### 4.2 ProjectManager 数据结构

```js
workspace = {
  dirPath: "data/",
  activeProjectId: "proj_A",
  projects: {
    "proj_A": {
      config: { version, projectName, profile, groups, apis: [...] },
      apiDataCache: { "api_001": { ...场景数据... }, "api_002": { ... } },
      apiHistoryCache: { "api_001": [...], "api_002": [...] },
      dirtyApiConfigs: Set<apiId>,    // 待落盘的 API 文件
      isDirty: false                  // config.json 或 API 文件有未保存更改
    },
    "proj_B": { ... }
  }
}
```

### 4.3 加载流程

```
loadWorkspace(dirPath, onProgress)
├── 扫描目录，发现所有项目
├── 遍历每个项目
│   ├── 读取 config.json
│   ├── 遍历 apis[] 索引
│   │   ├── 检查 apis/{id}_config.json 是否存在    ← 完整性检查 ①
│   │   ├── 读取该文件到 apiDataCache
│   │   ├── 验证文件内 id 字段一致性                  ← 完整性检查 ③
│   │   └── onProgress(loaded, total)                ← 进度回调
│   ├── 扫描 apis/ 目录下所有 *_config.json
│   │   └── 反向检查是否在索引中                      ← 完整性检查 ②
│   └── 自动修复：从索引移除文件缺失的条目
├── 汇总 issues[] 返回
└── 开启 auto-save（5s 间隔，持续运行）
```

### 4.4 写操作策略：缓存优先 + 脏标记 + 自动落盘

**当前：** 用户操作 → writeFile 直接写盘 + 更新缓存

**改造后：**

```
用户操作 → saveAPIConfig(id, data)
         → 只更新 apiDataCache
         → dirtyApiConfigs.add(id)
         → markDirty()
                  ↓
自動保存(5s) → 遍历 dirtyApiConfigs，逐个写 apis/{id}_config.json
            → 写 config.json（若 isDirty）
            → 清空 dirtyApiConfigs
            → isDirty = false
```

涉及的方法：

| 方法 | 改动 |
|------|------|
| `saveAPIConfig(id, data)` | 更新缓存 + `dirtyApiConfigs.add(id)` + `markDirty()` |
| `addAPI(api)` | 更新缓存 + 索引 + `markDirty()` |
| `updateAPI(id, newData)` | 更新缓存 + 索引 + `dirtyApiConfigs.add(id)` + `markDirty()` |
| `deleteAPI(id)` | 移除缓存 + 索引 + `markDirty()` + 记录待删文件 |
| `softDeleteAPI(id)` | 仅改索引 + `markDirty()` |
| `saveProject()` | 被 auto-save 统一调度，写 config.json + 所有 dirty API 文件 |

### 4.5 项目切换流程

```
switchProject(targetId)
├── 当前项目 isDirty ？
│   ├── 是 → 弹窗 [保存并切换 / 放弃并切换 / 取消]
│   │   ├── 保存并切换 → 立即落盘当前脏数据 → 切换（零 I/O）
│   │   ├── 放弃并切换 → 丢弃脏数据 → 切换
│   │   └── 取消 → 不动
│   └── 否 → 直接切换 activeProjectId（纯内存操作）
└── 更新底部栏高亮、左侧 API 树、中间详情面板
```

### 4.6 完整性检查（C 级）

加载完成后收集的 issues 类型：

| 类型 | 检测条件 | 自动修复 | 说明 |
|------|----------|----------|------|
| `missing_file` | 索引中有条目，但 `apis/{id}_config.json` 不存在 | ✅ 从索引移除 | 可能原因：手动删文件 |
| `orphan_file` | `apis/` 目录下有 `*_config.json` 但不在索引中 | ❌ 不动文件 | 可能原因：索引损坏或未同步 |
| `id_mismatch` | 文件内 `id` 字段与文件名/索引不一致 | ❌ 仅报告 | 可能原因：手动编辑或残留文件 |

显示逻辑：
- 无 issues → 自动进入主界面，无任何弹窗
- 有 issues → EmbeddedProgress 隐藏进度条，展示问题列表 + 「忽略并进入项目」按钮

## 五、删除策略

| 操作 | 效果 | 引用检查 | 恢复 |
|------|------|----------|------|
| 删除场景 | 标记 `deleted: true`，UI 中隐藏 | 不检查 | 可从「已删除场景」恢复 |
| 删除 API | 标记 `deleted: true`，config.json 中保留索引 | 不检查 | 可从「已删除 API」恢复 |
| 永久删除场景 | 从 scenarios 中移除，若文件无有效数据则删文件 | 弹窗提示被引用次数，可选批量清除引用 | 不可恢复 |
| 永久删除 API | 删除索引 + 文件 | 弹窗提示被引用次数，可选批量清除引用 | 不可恢复 |

## 六、UI 改动要点

### 6.1 场景管理

- API 标题栏下方增加场景切换栏：`[场景 A ▼] [场景 B] [场景 C] [➕]`
- 点击场景名切换，当前场景高亮
- 点击 ➕ 复制当前场景创建新场景
- 每个场景可编辑名称和备注

### 6.2 Body 编辑器

- 同一个场景内切换 contentType（json/xml/text/html）：
  - 保存当前到 `body.contents[oldType]`
  - 从 `body.contents[newType]` 恢复
  - 归位 code 模式
- 每个 contentType 的 schema 独立保存，互不影响

### 6.3 执行与历史

- 发送按钮支持：`[发送当前场景] [▼ 批量运行所有场景]`
- 历史列表按场景分组或加一列场景名

### 6.4 删除交互

- 删除场景/API 时先逻辑删除
- 永久删除时弹窗级联引用检查：
  ```
  🔍 该 API 被以下位置引用：
  - api_user@scn_default → body.content (清理)
  - api_order@scn_001   → header.token  (清理)
  [取消] [永久删除] [永久删除并清除引用]
  ```

### 6.5 EmbeddedProgress 可复用进度组件

欢迎页面加载工作空间时展示，配置参数如下：

| Prop | 类型 | 说明 |
|------|------|------|
| `status` | `'loading'\|'done'\|'issues'\|'error'` | 当前状态 |
| `current` / `total` | `number` | 进度数据 |
| `message` | `string` | 状态描述文字 |
| `issues` | `{ type, apiId?, name?, message }[]` | 完整性问题列表 |
| `actions` | `{ label, onClick, primary? }[]` | 底部操作按钮 |

显示规则：
- `loading` → 进度条 + message（如"加载 API 配置 (23/156)"）
- `issues` → 隐藏进度条 → 展示 issues 列表 + 操作按钮
- `done` → 短暂闪过后自动消失/进入
- `error` → 显示错误信息 + 重试按钮

### 6.6 路径搜索增强

- 搜索范围：API 顶层 `api_path` + 各场景 `apiPath`
- 数据来源：全量预加载时已缓存到 `apiDataCache`，搜索时全内存匹配
- 配合已有 name / id / group / 场景名搜索，统一在 `getFilteredAPIs` 中处理

### 6.7 引用查找

- 入口：API 更多菜单（`MoreHorizontal` 按钮）新增「查看引用」
- 数据来源：遍历内存中所有项目的 `apiDataCache`，正则匹配 `{{ref:targetApiId...}}`
- 弹窗展示：
  - 按引用 API → 引用场景分组
  - 每行可点击，点击后调用 `onSelect` 跳转到该 API
- 无需额外 I/O，全内存操作

### 6.8 项目切换时的草稿确认

- 底部栏切换项目时，若当前项目有未保存更改（`isDirty`），弹出确认对话框：
  - [保存并切换] → 立即落盘 → 切换项目
  - [放弃并切换] → 丢弃脏数据 → 切换项目
  - [取消] → 不执行任何操作
- 无脏数据时直接切换（零 I/O）

- 每个场景展示：参数表 + 请求体 + 断言 + 最近执行结果

## 八、状态管理与版本兼容

### 8.1 测试阶段数据重置

当前处于测试阶段，存量数据不重要。实施改造时直接清空项目目录，按新格式保存。
旧版 `config.json` / `history.json` 不再兼容读取。

### 8.2 版本号

`config.json` 中保留 `version` 字段。后续结构变更需编写独立迁移工具处理，不在应用内嵌迁移逻辑。

### 8.3 缓存落盘策略

改造前各写方法直接写文件，改造后改为：

```
内存操作 → 标记脏 → 定时器统一落盘
         ↑           ↓
      saveAPIConfig  auto-save (5s)
      addAPI         ├─ 写所有 dirtyApiConfigs
      updateAPI      ├─ 写 config.json（若 isDirty）
      deleteAPI      └─ 删除待删文件
```

切换项目时若检测到 `isDirty`，弹窗让用户选择「保存并切换 / 放弃并切换 / 取消」。

## 十、注意事项

| 注意点 | 说明 |
|--------|------|
| Token compact | per-API 写操作已大幅降低单次体积，自动保存 5s 间隔进一步合并写操作 |
| 引用循环 | ref 链检测在场景级别进行，批量运行时要避免循环依赖 |
| 首次加载性能 | 工作空间加载时全量读入所有 API config，Electron 本地文件系统数百文件通常在百毫秒级；进度组件给予用户反馈 |
| 内存占用 | 所有 API 数据常驻内存，按单个 API config ~5KB 估算，500 个 API 约 2.5MB，可接受 |
| 自动保存 | 不可关闭（5s 间隔），切换项目时强制检查脏数据；退出应用前应确保落盘完成 |
| 完整性修复 | 只修复索引（移除文件缺失的条目），不删除孤立文件；orphan_file 类型可后续提供导入功能 |
